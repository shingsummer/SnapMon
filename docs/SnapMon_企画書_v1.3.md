## 1. コンセプト

### 1.1 一言で

身の回りの「物」を写真に撮るとモンスターになる。そのモンスターは、外に出て歩くことでしか強くならない。

### 1.2 元ネタとの差別化

| 要素 | 元ネタ | 本作での扱い |
|---|---|---|
| モンスターの誕生 | モンスターファーム（CD/音楽から生成） | 写真から生成。被写体の「何か」「色」「形」が種族・属性・見た目に反映される |
| 成長のランダム性 | モンスターファーム（個体差・寿命） | 成長タイプ（早熟／晩成／平均／波型／超晩成）と素質値をランダム付与し、どちらも非開示。「最初弱いが化ける」個体が存在。寿命は採用しない |
| 位置情報・歩行 | ポケモンGO | 歩数と歩行が育成の主エネルギー源。乗り物移動はカウントしない。位置情報（ジム）は v1.1 以降 |
| 収集制限 | 課金ガチャ全般 | 1日の生成枚数を固定上限にし、課金でも撮影枚数は増やせない |

### 1.3 設計上の四原則

1. **強さは歩いた量でしか買えない**: 課金・周回・連写で強くなる抜け道を作らない。
2. **育ててみないと分からない**: 素質と成長タイプは数値として一切開示しない。プレイヤーが知る手段は「実際に育てて成長グラフを見る」ことだけ。「早熟だから捨て、晩成だから育てる」という作業化を防ぐ。
3. **モンスターは死なない・捨てさせない**: 寿命なし。成長が止まった個体は「師匠」として次世代を支え、牧場に居続ける。保管数に上限を設けない。
4. **写真は思い出であり材料**: 撮った写真はモンスターの「出自」として図鑑に残る（本人の端末内のみ）。

### 1.4 ターゲット

- メイン: 20〜40代、ポケモンGO／モンスターファーム経験者、通勤・散歩習慣のある層
- サブ: 親子で遊ぶ層。**アカウントは保護者のもの**で、子どもが被写体を選び撮影し、保護者が歩いて操作する遊び方を想定。13歳未満の本人アカウントは作らない（§14.3）

### 1.5 プラットフォーム

- iOS 16 以上 / Android 10 以上
- 縦画面固定、オフライン時は閲覧のみ可能（歩数は OS 側に蓄積され、次回起動時に取り込む）。生成・トレーニング・バトルはオンライン必須

## 2. コアループ

```
[撮る] 1日3枚まで
   ↓ 画像認識 → シード生成 → ステータス確定 → アート割当（キャッシュ）
[生まれる] 初期ステータスのみ表示。成長タイプ・素質は永久に隠し値
   ↓
[歩く] 歩数 → 「活力ポイント（VP）」に変換（乗り物は除外）。パートナー1体に歩数経験値
   ↓
[育てる] VPを消費してトレーニング／アイテム使用 → ステータス上昇（成長タイプで伸び方が変わる）
   ↓
[戦う] フレンド非同期対戦（v1）／ジム・すれ違い・リーグ（v1.1 以降） → 報酬アイテム／VP
   ↓
[師匠・継承] Lv50 到達で「師匠」になれる → 新しく生まれる1体に素質の一部を継承（師匠は牧場に残り、バトルも可能）
   ↺
```

1セッションの想定時間: 撮影1分、育成操作2〜3分、バトル1〜2分。1日合計10分＋歩行時間。
1体を Lv50 にする目標日数: 集中して約25日、2体並行で約50日（§4.7）。

## 3. モンスター生成システム（写真→モンスター）

### 3.1 生成パイプライン

```
写真（端末）
 → ① 端末内前処理（縮小 1024px、EXIF除去、顔検出→顔があれば撮り直し要求）
 → ② サーバーへ送信（HTTPS、認証必須）
 → ③ 画像認識API: ラベル(上位5)・主要色(上位3)・アスペクト比・輝度 を取得
 → ④ シード計算: hash(ラベル1, 主要色1, userId, 日付, サーバー乱数)
 → ⑤ 種族決定 / 属性決定 / ステータス・成長タイプ・素質を乱数決定（§4）
 → ⑥ アートバケット決定（§3.6）。キャッシュ済みなら即返却。未生成なら画像生成APIにジョブ投入
 → ⑦ Monsterレコード作成、クライアントに返却
```

- ③〜⑦はすべてサーバー側で行う。クライアントはステータス乱数を一切生成しない（改ざん防止）。
- ⑥で新規生成が必要な場合のみ非同期。生成完了まではシルエット（卵）表示。通常30〜60秒。運用が進むほどキャッシュ命中率が上がり、ほとんどの誕生は即時になる。
- 生成失敗時はリトライ2回、失敗ならその日の撮影枠を返却してユーザーに再撮影を促す。

### 3.2 種族（ファミリー）決定ルール

画像認識ラベルを 12ファミリーにマッピングする。ラベル辞書はサーバー側JSONで管理し、無料で更新できるようにする。

| ファミリー | 対応ラベル例 | 基本傾向 |
|---|---|---|
| ビースト | 犬, 猫, ぬいぐるみ, 毛皮 | 攻撃・速さ寄り |
| プラント | 花, 木, 野菜, 観葉植物 | HP・回復寄り |
| メタル | 工具, 車, 鍵, 缶 | 防御寄り |
| アクア | ペットボトル, コップ, 水, 魚 | バランス |
| ロック | 石, 建物, コンクリート | 防御・HP |
| スパーク | 電化製品, ケーブル, 照明 | 速さ・特攻 |
| ゴースト | 古い物, 人形, 暗い写真 | 特攻・回避 |
| フード | 食べ物, 菓子, 果物 | HP・運 |
| ペーパー | 本, 書類, 段ボール | 賢さ・回避 |
| クロス | 服, 靴, 布 | 速さ・バランス |
| トイ | おもちゃ, ゲーム機, フィギュア | 運・波型成長多め |
| エニグマ | 認識信頼度が低い／該当なし | 全ランダム、大当たり率も高い |

複合被写体（例: 猫のぬいぐるみ）は、ラベル上位2つが別ファミリーなら「サブファミリー」を持ち、見た目と技に両方が反映される。

### 3.3 属性（エレメント）決定ルール

主要色1位から決定。火（赤・橙）、水（青）、草（緑）、雷（黄）、光（白・淡色）、闇（黒・濃色）、無（灰・茶・複合）。相性は3すくみ＋光闇相互有利。

### 3.4 同じ物を撮ったときの挙動

シードに `userId` と `日付` を含めるため、同じマグカップを撮っても毎日違う個体になる。ただし種族と属性は同じになるため「この系統を狙う」遊びは成立する。

### 3.5 撮影バリデーション

- 人物の顔が検出された場合: 生成拒否、撮影枠は消費しない（プライバシー保護）
- スクリーン（ディスプレイ）撮影の検出: 認識ラベルに「screen/monitor」が上位にある場合は生成可だが「エニグマ」に強制。画面越しの画像検索連打を無意味化する
- 極端な暗さ／ブレ: 認識信頼度が0.3未満ならエニグマ

### 3.6 アートのキャッシュ方式（v1.3 で個体ごと生成から変更）

画像生成は最大コストであり、個体ごとに生成すると無料ユーザー1人あたり月150〜450円のコストになり収支が成立しない（§14.2）。そのため **アートは「バケット」単位で生成しキャッシュ共有**する。

- バケットキー: `family × subFamily(なし含む) × element × colorBucket`
  - `colorBucket` は主要色1位を 色相12段階 × 明度3段階 = 36 に量子化
  - 想定バケット数: 12 × 13 × 7 × 36 ≒ 39,000 だが、実際に出現するのは偏るため運用初期で数百、1年で数千程度
- 初めて出現したバケットのみ画像生成APIを呼び、Storage に保存。以降の同バケットは同じ画像を返す。
- **個体差の出し方**（端末側、コストゼロ）:
  - 主要色2位・3位から算出した微小な色相・彩度シフト（±8°、±10%）をシェーダで適用
  - 出自ラベルに応じた小さな装飾（例: マグカップ→取っ手の飾り）は v2 で検討
  - 名前・出自写真・成長グラフ・家系図が個体の「個性」の主体。見た目より物語で差別化する
- **専用アート生成（有料、240円/体）**: 出自写真の特徴を反映した、その個体だけの 2048px アートを生成する。§12 の収益源であり、生成コストを直接回収する。
- 事前生成: リリース前に「主要 12 ファミリー × 7 属性 × 明度3」の 252 枚をベースとして生成しておき、初日から卵待ちがほぼ発生しないようにする。

## 4. ステータスと成長タイプ

### 4.1 ステータス6種

| 略称 | 名称 | 役割 |
|---|---|---|
| HP | 体力 | 0で戦闘不能 |
| ATK | 攻撃 | 物理技の威力 |
| DEF | 防御 | 物理被ダメ軽減 |
| SPA | 特攻 | 属性技の威力。**属性技の被ダメ軽減も兼ねる** |
| SPD | 速さ | 行動順・回避 |
| LUK | 運 | 会心率・アイテムドロップ率 |

各ステータスの上限は 999。合計値（BST）で総合ランクを表示する。

### 4.2 個体が持つ隠しパラメータ

| パラメータ | 範囲 | 説明 | プレイヤーへの見え方 |
|---|---|---|---|
| 初期値 `base[s]` | 5〜60 | 生まれた時のステータス | 即時表示 |
| 素質 `talent[s]` | 1〜10 | 最終到達点を決める。10なら999まで届く | **永久に非表示**。数値・ランク・星などいかなる形でも出さない |
| 成長タイプ `growth` | 早熟／平均／晩成／波型／超晩成 | 伸び方の曲線 | **永久に非表示**。成長グラフ（実績値の推移）だけが手がかり |
| 性格 | 8種 | 好むトレーニングで効率±20% | 3回トレーニングで表示（育成の手触りに関わるので開示） |

**非開示の徹底ルール（実装者向け）**
- API レスポンスに `talent` `growth` を含めない。クライアントは存在自体を知らない。
- 成長グラフはレベルごとの実測ステータスをそのまま描く。予測線・上限線は描かない。
- 「伸びしろ」「期待値」を推定して表示する機能は作らない。ソート項目にも入れない。
- 例外: 図鑑の「生涯記録」にも載せない（Lv50 到達後も非開示。プレイヤーが「あの子は晩成だったんだな」と思うのは自由）。
- フレーバーテキストによる「示唆」は採用する。ただし §4.6 の「解析されない」ルールに従うこと。

### 4.3 「最初強いが伸びない／最初弱いが化ける」の実装

初期値と素質を **負の相関** で振る。

```
raw_base   = rand(5, 60)                  # 各ステータス独立
raw_talent = rand(1, 10)
talent[s]  = clamp( round( raw_talent * 0.6 + (65 - raw_base) / 60 * 10 * 0.4 ), 1, 10 )
```

この式の性質（`tools/sim_growth.py` で確認済み、相関係数 −0.52）:

| 初期値 | 取りうる素質 |
|---|---|
| 5 | 5〜10 |
| 20 | 4〜9 |
| 40 | 2〜8 |
| 60 | 1〜6 |

- **初期値が低い個体は素質5未満にならない**。「弱い子を育てても損しない」を式レベルで保証している。
- **初期値が高い個体は素質6が上限**で、999 には届かない。「最初強いが完成が早い」個体になる。これは意図した仕様。
- 素質の分布は 5〜6 が最頻（各約17%）、1 と 10 は各約1.5%。

さらに成長タイプの抽選確率を初期値合計（BST0）で変える。

| BST0 | 早熟 | 平均 | 晩成 | 波型 | 超晩成 |
|---|---|---|---|---|---|
| 250以上（強い） | 50% | 35% | 10% | 5% | 0% |
| 150〜249 | 20% | 45% | 20% | 10% | 5% |
| 149以下（弱い） | 5% | 25% | 35% | 15% | **20%** |

超晩成は Lv30 までほぼ伸びないが、以降は素質上限まで一気に伸びる。「弱いのに手放さなかった人だけが強い個体を得る」を実現する。

### 4.4 レベルと成長曲線

- レベル上限: 50
- 経験値はトレーニング・バトル・歩行（パートナーのみ）で獲得（§4.7）。
- レベルアップ時のステータス上昇量:

```
gain[s] = ( levelGainBase + levelGainPerTalent * talent[s] )
          * curve(growth, level) * personalityMod(s) * rand(0.8, 1.2)

levelGainBase      = 5.0    # 素質に関係なく全個体が伸びる底上げ分
levelGainPerTalent = 0.9    # 素質1あたりの追加分

curve(早熟,  L) = 2.0 - L/50 * 1.5   # 序盤2.0 → 終盤0.5
curve(平均,  L) = 1.25
curve(晩成,  L) = 0.5 + L/50 * 1.5   # 序盤0.5 → 終盤2.0
curve(波型,  L) = 1.25 + 0.75 * sin(L / 4)
curve(超晩成,L) = L < 30 ? 0.3 : 2.56
```

v1.2 からの変更点: v1.2 の `gain = talent * curve * …` は総上昇量が「素質 × 62.5」に比例し、素質1の個体が Lv50 で 70 前後にしか届かず、§4.5 の上限緩和（459）が絵に描いた餅になっていた。底上げ分 5.0 を加えることで、**レベルアップだけで全個体が上限の 80〜92% に到達**し、残りをトレーニング（10〜27回）で埋める設計に変えた。

全成長タイプで Lv1→49（レベルアップ49回）の curve 合計がほぼ等しくなるよう定数を調整済み（§16.4）。

### 4.5 素質によるステータス上限と最終到達点の目安

各ステータスの個体上限は `statCap[s] = 399 + talent[s] * 60`（素質1 = 459、素質5 = 699、素質10 = 999）。レベルアップ・トレーニング・強化石のどれで上げてもこの上限を超えない。

最低でも 459 に届けば実用圏（低ランクリーグ・フレンド戦）で使えるため、どの個体を育てても損にならない。素質は「最強を目指すときだけ効く差」に留める。

到達例（`tools/sim_growth.py` の 2000 回試行平均、レベルアップのみ・トレーニングなし）:

| 個体 | Lv30 | Lv40 | Lv50 | 上限 | 上限までのトレーニング回数 |
|---|---|---|---|---|---|
| 素質10 / 初期60 / 早熟 | 689 | 824 | 917 | 999 | 約10回 |
| 素質10 / 初期10 / 超晩成 | 132 | 490 | 849 | 999 | 約19回 |
| 素質5 / 初期30 / 晩成 | 292 | 438 | 612 | 699 | 約16回 |
| 素質3 / 初期40 / 平均 | 319 | 416 | 512 | 579 | 約15回 |
| 素質1 / 初期5 / 平均 | 219 | 292 | 366 | 459 | 約27回 |

- 早熟の素質10は Lv30 で 689、超晩成の素質10は Lv30 で 132。同じ素質でも Lv30 時点で5倍の差があり、Lv50 で追いつく。これが「化ける」体験の中身。
- 素質1でも Lv50 で 366、トレーニングで 459。フレンド戦・低ランク帯では戦える。

上限到達を明示するUI（光る・「MAX」表示など）は **作らない**。上限値から素質が逆算できてしまうため。プレイヤーは成長グラフが平らになったことで気づく。ただしトレーニング画面で上限到達済みステータスを選んだ場合は VP を消費せず「もう伸びないようだ」とだけ返す（VP の無駄打ち防止）。

**定数を変更したら必ず `tools/sim_growth.py` を実行し、この表と §16.4 を更新すること。**

### 4.6 つぶやきシステム（成長タイプの示唆）

モンスターは時々ひとこと「つぶやく」（詳細画面・ホームのパートナー表示・トレーニング後）。このつぶやきの中に、成長タイプをうっすら示唆するものを混ぜる。目的は「Lv20で超晩成を諦めて保管送りにする」を減らすこと。

**設計の大前提: 「Lv○○になったら出る」「○日放置したら出る」のような、プレイヤーが条件を特定できる仕組みにしない。また、繰り返し呼び出して統計的に推定することもできないようにする。** そのために以下を守る。

1. **トリガーはレベルでも日数でもなく確率**。レベルアップ・トレーニング完了・歩数同期時にそれぞれ独立に抽選する。示唆つぶやきの出現率は成長タイプごとの「示唆ウィンドウ」内で 1回あたり 8%、ウィンドウ外では 1%（ゼロにしない）。
   - 超晩成のウィンドウ: Lv12〜28（個体ごとに開始Lvを ±4 ランダムにずらす）
   - 晩成: Lv10〜25、早熟: Lv5〜15、波型: 常時 3%、平均: 常時 1%
2. **同じテキストを複数の成長タイプで使う。すべてのテキストに全5タイプの重みを持たせる（0 にしない）**。例えば「最近目つきが変わった気がする」は超晩成 50%・晩成 25%・波型 10%・早熟 5%・平均 10% の重みで出る。どのテキストも単独では確定情報にならず、「このセリフが出たので平均ではない」という消去法も成立しない。
3. **示唆つぶやきと無関係なつぶやきを同じ見た目で出す**。「今日の散歩は楽しかった」「あの写真の場所、また行きたい」など無関係なものが全体の 85% 以上を占め、示唆つぶやきだけ目立つUIにしない。
4. **サーバー側で抽選し、抽選ログは保存しない**。テキストのIDだけをクライアントに返す。
5. **つぶやき専用の API を作らない**（v1.3 で `getMurmur` を廃止）。抽選は `train` `submitSteps` `startBattle` の処理内で行い、レスポンスに `murmurTextId?` として同梱する。これらは VP・回数・レート制限で呼び出し回数が物理的に縛られているため、改造クライアントで何百回も引いて出現率の差（8% vs 1%）から統計的に推定することができない。詳細画面での表示は、直近に受け取った ID をクライアントがキャッシュして再表示するだけ。
6. **テキストプールは運営側で追加・入替可能**（shared-config の `murmurs.json`）。攻略サイトで対応表が出回っても、重みと文言を入れ替えれば無効化できる。
7. 「まったく出ない個体」も存在させる（個体ごとに `murmurRate` を 0.5〜1.5 倍でランダム化）。無口な子は無口。

つぶやき例（示唆系）: 「最近目つきが変わった気がする」「まだ本気を出していないような顔をしている」「ずいぶん落ち着いてきた」「今が一番元気なのかもしれない」「なにかを溜め込んでいるように見える」
つぶやき例（無関係）: 「散歩のあとは機嫌がいい」「雨の日はじっとしている」「出自の写真をじっと見ている」

期待される体験: 「なんか意味深なこと言ってたから、もうちょっと育ててみるか」。確定情報ではなく、迷いを後押しする程度。

### 4.7 経験値とレベル到達ペース（v1.3 で追加）

師匠システムが「何日目に起動するか」を設計値として持つ。

```
expToNext(L) = 20 + 4 * L          # Lv1→50 の合計 5,880
```

| 経験値の獲得源 | 量 | 備考 |
|---|---|---|
| トレーニング1回 | 15 | 1日最大8回 = 120 |
| バトル勝利 / 敗北 | 20 / 8 | |
| 歩行（パートナーのみ） | 100歩 = 1 exp、1日最大 120 | ホームに表示中の1体にだけ入る。「今日は誰と歩くか」を選ぶ |
| 餌（ファミリー一致） | 30 | |

目標ペース（`tools/sim_growth.py` で計算）:

| 遊び方 | Lv50 までの日数 |
|---|---|
| 1体に集中（トレ8回＋歩行約60＋バトル3回/日） | 約25日 |
| 2体並行 | 約50日 |
| 歩くだけ（パートナー指名のみ） | 約100日 |

「毎日3枚生まれるが、育てられるのは同時に1〜2体」というボトルネックが本作の選択の核。どれを育てるかの判断に、隠された成長タイプとつぶやきが効く。

## 5. 育成システム

### 5.1 活力ポイント（VP）: 歩行の通貨

- 端末の歩数計から **歩数** を取得し、サーバーで VP に変換する。
- 変換レート: `100歩 = 1 VP`。1日の上限は `12,000歩 = 120 VP`（歩きすぎ防止・健康配慮）。
- 追加ボーナス: 30分以上の連続歩行を1日1回達成で +10 VP。

### 5.2 乗り物除外ロジック（v1.3 で GPS 速度判定を廃止）

v1 は位置情報の権限を一切要求しない。そのため GPS 速度による判定は使わず、**OS のアクティビティ認識と歩数の物理妥当性のみ**で判定する。

| 判定材料 | 実装 |
|---|---|
| OSのアクティビティ認識 | iOS: `CMMotionActivity`（walking / running / automotive / cycling / stationary）、Android: `ActivityRecognition API` |
| 歩数の物理妥当性 | 1分あたり 220歩 超は無効（振り機対策） |
| 静止中の歩数 | アクティビティが `stationary` の区間の歩数は無効 |
| 同期 | **バックグラウンド送信はしない**。アプリ起動時・フォアグラウンド復帰時に、前回同期以降の歩数とアクティビティ履歴を OS から取得し（iOS: `CMPedometer` は7日分、Android: Health Connect）、5分区間に分割してサーバーに送信。サーバーが最終判定 |

走る（running）は歩行扱いで有効。自転車（cycling）・自動車（automotive）は無効。アクティビティが取得できない区間（unknown）は歩数の物理妥当性のみで判定し受理する（除外しすぎて「歩いたのに増えない」体験を作らない）。

v1.1 でジム（位置情報）を入れる際も、GPS 速度は位置偽装検知にのみ使い、歩数判定には使わない。

### 5.3 トレーニング

VPを消費してステータスを上げる。1回 10 VP、1日最大8回（=80 VP）。残りのVPはアイテム交換や翌日繰越（上限200 VP）。

| トレーニング | 主上昇 | 副上昇 | 疲労 |
|---|---|---|---|
| ダッシュ | SPD | ATK | 中 |
| 力仕事 | ATK | HP | 高 |
| 瞑想 | SPA | LUK | 低 |
| 耐久 | DEF | HP | 高 |
| 散歩（自動） | 全て微増 | — | なし |

- 疲労が100を超えると翌日までトレーニング不可。休息（VP消費なし）で回復。
- トレーニングによる上昇はレベルアップ上昇とは別の「加算値」で、`rand(2, 4) + talent[s] * 0.5`（v1.2 の `rand(1,3) * talent/5` は素質1で1回 0.4 しか伸びず、上限まで約1,000回必要だったため変更）。

### 5.4 アイテム

写真からモンスターを生成した際、被写体のファミリーに応じたアイテムが **1〜3個** 同時に出る。バトル報酬でも入手。

| アイテム分類 | 効果例 |
|---|---|
| 餌（ファミリー別） | 対応ファミリーのモンスターに与えると経験値 +30、性格一致で疲労回復 |
| 強化石 | 特定ステータス +5〜+15（素質上限は超えない。上限到達済みなら消費されない） |
| 絆カプセル | 師匠になるときの継承率を上げる |
| 疲労回復薬 | 疲労を 0 にする（1日1個まで使用可） |

鑑定書・延命薬は v1.1 で廃止（§4.2 非開示ルール、§5.5 寿命廃止による）。

### 5.5 師匠と継承（寿命の代替）

寿命は存在しない。モンスターは死なず、引退もしない。成長の終わりは Lv50 到達（または全ステータス上限到達）で、それ以降もバトル・図鑑・着せ替えは通常どおり使える。

- Lv50 に到達した個体は「師匠」に任命できる（任意・取消不可）。
- 師匠は **1体につき1回だけ** 「弟子」を指名できる。弟子は「次に生まれるモンスター」で、生成時に師匠の素質の一部（各ステータス素質の 30%、絆カプセル使用で 50%）が上乗せされる（上限10）。
- 師匠は牧場に残り、ステータスも技もそのまま。弟子の詳細画面に「師匠: ○○」が表示され、師匠側にも「弟子: △△」が表示される。
- 弟子がさらに Lv50 になれば孫弟子を指名でき、系譜が図鑑に「家系図」として残る。累積で理想個体に近づくのが長期目標。
- 継承の中身（素質）は非開示のまま。プレイヤーには「師匠の力が受け継がれた」演出のみ。

**師匠の型（技の継承）**

- 師匠を任命するとき、師匠が覚えている 4 技のうち **1つ** を「師匠の型」として選ぶ（選んだ後は変更不可）。
- 弟子は誕生時にその技を **5枠目の専用スロット** に持って生まれる。通常の 4 枠は §6.3 のとおり自分のファミリー・属性から習得する。
- 師匠の型は弟子のファミリー・属性と無関係に使える（アクア族の弟子がビースト族の技を持てる）。これが家系ごとの個性になる。
- 弟子が師匠になるとき、師匠の型をさらに次へ渡せる（自分の 4 技から選んでも、受け継いだ師匠の型をそのまま渡してもよい）。3 代続けて同じ技が受け継がれると技名に「〜・伝承」が付き、威力 +10%（見た目と物語のためのボーナス、上限はここまで）。
- 家系図（S14）には各世代の師匠の型が表示される。

技継承はポケモンの「タマゴ技」に近い仕組みだが、本作では (a) 1 技のみ、(b) 専用スロットで通常枠を圧迫しない、(c) 系譜で見えることが目的、の 3 点で差別化する。強さより「うちの家系はずっとこの技」という愛着を狙う。

これにより「育てきった個体を手放す悲しさ」をなくし、逆に「最初に育てた1体がずっと家系の始祖として残る」体験にする。

## 6. バトルシステム

### 6.1 基本ルール

- 1対1、ターン制、最大 10 ターン、3体パーティから1体ずつ出す（勝ち抜き）。
- 行動は「技（4つまで、弟子は5つ）」から選択。オートバトルあり（非同期対戦向け）。
- 行動順: SPD 順。同値はランダム。
- **移動中ロック**: アクティビティ認識が automotive / cycling の間はバトル開始不可（歩きスマホ・運転中操作の抑止。位置情報は使わない）。

### 6.2 ダメージ式

```
物理技: damage = ( power * ATK / DEF ) * 0.4 * typeMod * crit * rand(0.9, 1.1)
属性技: damage = ( power * SPA / SPA ) * 0.4 * typeMod * crit * rand(0.9, 1.1)
                                  ^^^ 相手の SPA（特防を兼ねる。ステータスは6種のまま）

typeMod = 1.5 / 1.0 / 0.67
crit    = LUK/1000 の確率で 1.5倍
```

Lv50・平均ステータス（500）同士で、1発 15〜20% の HP を削る調整。この式では `power` の目安が 190〜250 になるため、moves.json の威力はその尺度で定義する（ポケモン的な 40〜120 の尺度ではない）。

### 6.3 技

- ファミリーで 6 技、属性で 4 技のプールがあり、生成時に 2 技、レベルアップ（Lv10/20/30/40）で 1 技ずつ習得候補。
- サブファミリーがある個体は両方のプールから習得可能。
- 弟子は上記 4 枠に加えて「師匠の型」1 枠を持つ（§5.5）。バトルでは 5 技から選択。

### 6.4 対戦モード

| モード | 内容 | 報酬 | 導入時期 |
|---|---|---|---|
| フレンド | コード交換して非同期対戦。相手のパーティはサーバー上のスナップショット | 少量 VP、アイテム | **v1** |
| ジム | 実在のPOI（公園・駅など、OpenStreetMap ベース）に紐づく。半径 80m 以内で挑戦。防衛モンスターを置ける | VP、アイテム、ジムコイン | v1.1 |
| 週間リーグ | レート制。同ランク帯と非同期マッチ | ランク報酬（見た目アイテム） | v1.2 |
| すれ違い | Bluetooth/位置で近くにいたプレイヤーと自動非同期対戦 | 少量 VP | v2（iOS のバックグラウンド BLE が難所のため最後） |

v1 でフレンド戦に報酬を付けるのは、v1.2 の「名誉のみ」だと v1 に報酬付きバトルが存在しなくなるため。

### 6.5 ジムの占有バランス（v1.1）

- 1ジムに置けるのは 1人1体、最大 6体。
- 防衛モンスターは 24時間で自動帰還（張り付き防止）。
- 同一ジムへの挑戦は 1日 3回まで。

## 7. 制限と不正対策

### 7.1 1日の制限（コアバランス）

| 項目 | 上限 | 備考 |
|---|---|---|
| 写真→モンスター生成 | **3枚／日** | 課金でも増えない。日付はサーバーの JST 0:00 でリセット |
| 育成中モンスター（アクティブ枠） | 30体（無料）／100体（プレミアム） | 超えたら「保管牧場」へ移動（解放は任意。デフォルトで解放ボタンを目立たせない） |
| 保管牧場 | **上限なし** | 保管中はトレーニング不可、バトル参加不可。いつでもアクティブに戻せる。v1.2 の 500 体上限は「捨てさせない」原則と矛盾するため撤廃。アートはキャッシュ共有なので 1 体あたりのストレージは数 KB |
| VP獲得 | 120 VP／日（12,000歩） | |
| トレーニング | 8回／日 | |
| フレンド戦 | 10回／日 | 報酬は先着 3 回まで |
| ジム挑戦（v1.1） | 同一ジム 3回／日 | |

### 7.2 不正対策

| 不正 | 対策 |
|---|---|
| 歩数偽装（振り機） | 220歩/分 超の区間無効、アクティビティ認識が `stationary` の区間は無効 |
| 端末時計操作 | すべての日付判定はサーバー時刻 |
| 写真の使い回し | 画像ハッシュ（pHash）を保存し、同一ユーザーの過去写真と 95% 以上一致（64bit 中 3bit 差以内）なら生成拒否（枠は消費しない）。90% では同じ机の別の物まで弾いたため引き上げ |
| ステータス改ざん | ステータス・乱数はすべてサーバー生成、クライアントは表示のみ |
| API直叩き | Firebase App Check（iOS: DeviceCheck / Android: Play Integrity）必須 |
| つぶやきの統計推定 | つぶやき専用 API を持たない（§4.6-5）。実イベントの副産物としてのみ返す |
| 位置偽装（v1.1） | サーバーで移動速度の連続性を検証（瞬間移動検知）。iOS: `isSimulatedBySoftware`、Android: `isFromMockProvider` を送信させる。違反3回で7日間の位置系機能停止 |

## 9. 技術構成

### 9.1 選定と理由

| レイヤ | 採用 | 理由 |
|---|---|---|
| クライアント | **Flutter 3.x（Dart）** | iOS/Android 単一コード。カメラ・歩数のプラグインが揃い、Claude Code との相性が良い。UIの自由度が高い |
| 状態管理 | Riverpod 2 | テスト容易、非同期に強い |
| ローカルDB | Drift（SQLite） | 同期済み歩数区間の記録、キャッシュ |
| バックエンド | **Firebase**（Auth, Firestore, Cloud Functions 2nd gen, Storage, App Check, FCM）。**最初から Blaze プラン**（Functions 2nd gen と外部API呼び出しに必須。無料枠内なら請求はほぼ 0 円。予算アラートを月 5,000 円で設定） | 個人開発で運用負荷が最小。Functions は TypeScript |
| 画像認識 | Google Cloud Vision API（Label Detection + Image Properties + Face Detection） | ラベル・主要色・顔検出を1回のリクエストで取得できる |
| 画像生成 | OpenAI Images API（gpt-image 系）を第一候補。差し替え可能なアダプタ層を用意し Stability / Google Imagen にも切替可。**バケット単位でキャッシュ**（§3.6） | 商用利用可・日本語プロンプト可・出力サイズ指定可 |
| 歩数 | iOS: `pedometer`（`CMPedometer` 履歴 + `CMMotionActivity`）、Android: Health Connect + ActivityRecognition。**起動時に履歴を取得、バックグラウンド処理なし** | Health Connect は Play Console で用途申告（Health Connect declaration）が必要。P1 中に申請する |
| 地図・POI（v1.1） | flutter_map（OpenStreetMap）＋ Overpass API で公園・駅を取得しジム候補にする | Google Maps SDK の従量課金回避 |
| 分析 | Firebase Analytics + Crashlytics | |
| CI | GitHub Actions（テスト）＋ Codemagic または fastlane（ストア提出） | |

### 14.2 変動費と収支（v1.3 でキャッシュ方式に変更）

**v1.2 の個体ごと生成の場合（廃止した理由）**: 1,000 DAU・生成率 50%・3枚/日で月 45,000 枚 × 3〜6円 = 月 14〜27万円。プレミアム転換率を 5% と楽観しても月 2.4 万円の収入で、無料ユーザー1人あたり月 150〜450 円の赤字が構造的に残る。

**v1.3 キャッシュ方式**:

| 項目 | 単価目安 | 1,000 DAU/月 |
|---|---|---|
| Vision API（3機能） | 約 0.7円/枚 | 約 3万円（45,000枚） |
| 画像生成（新規バケットのみ） | 約 5円/枚 | 運用初期 数千円、安定後 数百円 |
| 事前生成 252 枚 | 約 5円/枚 | 約 1,300円（1回のみ） |
| 専用アート生成（有料） | 約 10円/枚（2048px 高品質） | 240円の売上に対し原価 10円 |

Vision API が主コストになる（1ユーザー月 30〜45 円）。これは広告 1 日 1 回のリワード視聴（1 表示 1〜3 円）とプレミアム転換 3% でおおむね相殺できる。**P3 の完了条件に「1バケットあたり生成コスト」「キャッシュ命中率」の実測を含める。** Vision API も、Label Detection のみ（1機能）に減らせるか P1 で検証する（主要色は端末側で算出可能、顔検出は端末内 ML Kit で済む可能性が高い）。

### 14.3 リスクと対応

| リスク | 対応 |
|---|---|
| 写真に人・他人の物・個人情報が写る | 端末内で顔検出→拒否。出自写真は本人の端末／本人のみ読めるStorageに限定。他ユーザーには共有アートのみ公開 |
| 生成画像が既存キャラクターに似る | プロンプトに「既存キャラクター名・作品名を含めない」、ネガティブプロンプト。バケット数が有限なので **全バケット画像を人手レビュー可能**（キャッシュ方式の副次効果） |
| 画像生成APIの規約変更・値上げ | アダプタ層で差し替え可能にする（§9.1）。生成済みバケットは資産として残る |
| 健康配慮 | 1日 12,000歩で VP 上限。それ以上歩いても「無駄」にする |
| 移動中の操作 | アクティビティ認識が automotive / cycling の間はバトル開始をロック |
| 未成年 | Apple / Google サインインは年齢を返さないため、**初回起動時に生年を自己申告**させ、13歳未満は登録不可。親子層は保護者アカウントで遊ぶ想定（§1.4）。位置共有機能（v1.1）はデフォルトオフ |
| 法務 | 利用規約、プライバシーポリシー（個人情報保護法・APPI、歩数・生体情報の扱い）、特定商取引法表記（課金）、資金決済法（ゲーム内通貨 VP は無償付与のみで課金購入不可にして対象外に） |
| ストア審査 | 「ユーザー生成コンテンツ」要件（通報・ブロック機能）が必要。フレンド機能に通報・ブロックを v1 から実装。Android は Health Connect の用途申告が通らないとリリース不可（P1 で申請） |
| 位置情報ゲームの安全性（v1.1） | ジムは公共POIのみ |

## 15. 実装の進め方（Claude Code への指示）

以下は VSCode 上の Claude Code に対する作業指示である。

### 15.1 最初にやること

### 15.2 フェーズ順守

§13 の P0→P7 の順で進める。各フェーズは「完了条件」を満たすまで次に進まない。画像生成 API（P3）はコストが絡むため、P1〜P2 はプレースホルダ画像（ファミリー×属性の SVG シルエット 84 種）で進める。v1.1 以降の機能（位置情報・ジム・リーグ・すれ違い）は v1 リリースまで着手しない。

### 15.3 コーディング規約

- Dart: `flutter_lints` 準拠、`domain/` は Flutter 非依存の純 Dart にしてテスト可能に。
- TypeScript: `strict: true`、`zod` で callable の入力を検証。
- 乱数はすべて `seed` 付きで再現可能にする（`seedrandom` / Dart は自前 xorshift）。
- すべての callable に 1 つ以上のユニットテストとエミュレータ統合テスト。
- `monsters_private` を読むコードは `functions/src/` にしか存在してはならない。クライアントの DTO 型に `talent` `growth` というフィールド名を作らない（lint で禁止語にする）。
- コミットは 1 機能 1 コミット、日本語 OK。

### 15.4 人間（しぴ）に依頼が必要な作業

- 正式タイトル（仮: SnapMon）
- 技の名称・演出（moves.json の日本語名）
